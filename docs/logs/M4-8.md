### 2026-10-15 — session 1

- Started the task. Read the card, the milestone's Streams and Gate text, and AGENTS.md.
- `tests/multi/netns.sh` (new): the namespace set-up of `run_netns.sh` as functions both
  scripts source (`netns_enter`, `netns_nodes`, `netns_add`, `netns_run`); `run_netns.sh`
  now uses it. `run_netns.sh -d 5 build/dev/apps/readshare/readshare`: PASS, as before.
- A probe with real daemons in namespaces: `matmul 1024 1` took 1 s at 0 ms but more than
  300 s at 25 ms (every page fetch costs a round trip), and start-up takes 10 to 20 s. A
  fixed-size job cannot last long enough for a leave at 0 ms and finish at 25 ms. Asked the
  person; approved (below) to add a mode to the test program in `tests/unit/pmd_test.cpp`.
- `tests/unit/pmd_test.cpp`: M4-7's `join` mode becomes one of three modes that run in
  rounds of 2 ms chunks: `join` (until node 4 has run some), `until-stop` and
  `big-until-stop` (until the script creates `<report>.stop`; `big` over 8 MB of numbers),
  each at most 120 s, the last round checked. M4-7's test is unchanged and passes.
- `tests/multi/run_m4.sh` (new): three daemons, one in each namespace, with the chosen delay
  and loss; node 1 knows the others by `--peers`. Scenarios: `leave` (`pm leave` on node 3
  while it runs a chunk; exit 0, every number right, `member_left`), `join` (the same, then
  a fourth namespace and daemon with node 1 as its seed; node 4 runs chunks,
  `member_joined`), `abort` (node 3's worker killed; exit 1 within 3 s, "node 3 lost", no
  job process left), `spill` (`--cap-ram 1M`, spill budget 16 MB, 8 MB of numbers; exit 0,
  every number right, a spill file with data in it).
- My mistakes on the way, in the new script: state directories were reused between
  scenarios (a stale socket); background calls of the `netns_run` function gave a
  subshell's PID, so daemons were never stopped and held their ports (now `nsenter`
  directly); the spill sampler ran `readlink` on every descriptor of every process (238 s;
  now only the job's processes); and it gave the job 3 s to spill, which at 25 ms was not
  enough (one run of 24 failed). It now waits until a spill file has data, at most 120 s,
  then stops the job.
