### 2026-10-09 — session 2: the program, the script, and first numbers

- `apps/matmul/main.c` (C11), `matmul [--plain] [n] [threads]`. As a job it takes A, B and C
  from the shared region, fills A and B, and computes the rows of C with one
  `pm_parallel_for_data` call over C. `--plain` is the same arithmetic on one thread with
  `malloc`, and never calls ParaMesh. It prints the time of the multiplication, a checksum of
  C, and the chunks each node ran, which the task counts with `pm_atomic_add`.
  No test hook: `paramesh.h` only.
- `tools/bench/matmul.sh [-n nodes] [-s size] [-t threads] [-r runs] [-b build]`: runs the
  three ways, each `runs` times, and prints a table with the median, the range, the ratio to
  one node, the chunks by node of the last N-node run, and whether the checksums agree. It
  starts jobs with `tests/multi/run_local.sh`, and builds its own Release build in
  `build/bench` if there is none.
- Found on the way: a Release build of the library does not pass with warnings as errors (GCC
  13 reports possible null dereferences that only appear with optimisation on). The script
  builds with `PARAMESH_WERROR=OFF`. In `docs/TODO.md`.
- State: Done-when met. The numbers under Verification are the first measurement of the
  speed-up, and on one machine there is none yet: see "What the numbers say".

## Decisions

<!--
Choices you made inside the card's scope, each with the reason. Not for points listed under
"Still open" in the plan: those are asked, never decided here. Write "None" if there were none.
-->
- **One program, with `--plain`,** not two: the plain run then uses the very same loops.
- **The plain program uses one thread.** It shows the cost of the arithmetic itself; "ParaMesh
  on one node" is what the N-node run is compared with.
- **The matrices hold small whole numbers,** so every sum is exact in a double and the
  checksum is the same whatever order the rows were computed in. The script compares the
  three checksums and fails if they differ.
- **Chunk counts come from the program,** which adds 1 to a shared number for its node at the
  end of every chunk. The table of counts has one entry for each possible 16-bit node ID
  (512 KiB of shared memory, of which only the pages used are ever touched).
- **Jobs are started with `run_local.sh`** until `pmrun` exists (M3-5); M3-7 moves the
  applications onto it.
- **The script makes its own Release build:** the presets are all Debug, and timing a Debug
  build says little. It does not edit a shared build file.
- **Time is taken with C11 `timespec_get`,** the wall clock: the program stays plain C11 with
  no feature macro.

Local, 2026-10-09, host `ouroboros` (16 processors).

**Done-when: the application compiles against `paramesh.h`; the script produces a results
table.** The program builds in all eight builds with warnings as errors and includes only
`paramesh.h`. `tools/bench/matmul.sh` printed:

```text
Matrix multiply, n = 1024, 5 runs each, on ouroboros (16 processors).

| Way | Threads | Median (s) | Range (s) | Against one node |
| --- | --- | --- | --- | --- |
| Plain program | 1 | 0.188 | 0.186 to 0.191 | 0.69 |
| ParaMesh, 1 node | 2 | 0.130 | 0.120 to 0.134 | 1.00 |
| ParaMesh, 3 nodes | 3 x 2 | 0.161 | 0.158 to 0.219 | 0.81 |

"Against one node" is the one-node median divided by the row's median: above 1 is faster.
Chunks by node in the last 3-node run (node:chunks): 1:25
The three ways gave the same checksum, 6442435586.
```

Larger sizes, four threads on each node:

| n | Runs | Plain, 1 thread | 1 node, 4 threads | 3 nodes, 3 x 4 | Against one node | Chunks by node |
| --- | --- | --- | --- | --- | --- | --- |
| 2048 | 3 | 3.605 s | 0.957 s | 1.168 s | 0.82 | 1:33 2:8 3:8 |
| 4096 | 1 | 30.669 s | 8.051 s | 8.705 s | 0.92 | 1:28 2:11 3:10 |

Other runs: `matmul --plain 128`; `matmul 0` prints the usage and exits 2; three nodes with the
gcc ASan build; three nodes in network namespaces with 1 ms per link: all with the checksum
of the plain run for that size.

**What the numbers say.** The results are right and the work is shared (at n = 4096 the two
workers ran 21 of 49 chunks), but three nodes on this one machine are not faster than one
node: 0.92 at n = 4096. Two things are visible:

- The launcher fills A and B, so it holds every page of them. Each worker has to fetch all
  of B, 32,768 pages at n = 4096, one page for each round trip through the page's home, and
  waits for pages for much of the run.
- A worker with nothing to do asks again only every 200 ms at most, so in a short run the
  launcher's own threads finish before the workers have woken (n = 1024: node 1 ran all 25
  chunks).

The M3 gate asks for n = 4096 to be faster on two cabled laptops than on one (FR-9.2). This
is a different machine count and a real network, so it is not the gate's measurement, but it
is a warning for it. The stride prefetcher, which would fetch B's pages ahead of the faults,
is in `docs/TODO.md` as "after the M3 speed-up is measured".

Quality gate: all eight compiler and sanitizer builds pass, 15/15 tests (14/14 under TSan), no
warnings; clang-tidy exit 0 (the C program included); clang-format clean; `bash -n` on the
script.
