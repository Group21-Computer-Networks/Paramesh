### 2026-10-07 — session 2: every item tried by hand; Still open #17 answered

- Wrote a probe in C (scratchpad): `mmap` 4 GB at `0x600000000000` with
  `MAP_FIXED_NOREPLACE`, open userfaultfd with `UFFD_USER_MODE_ONLY`, `UFFDIO_API` asking for
  the write-protect feature, register the whole region for missing and write-protect faults,
  then on the first and the last page: a thread reads (missing fault, answered with
  `UFFDIO_COPY` in write-protect mode) and writes (write-protect fault, answered with
  `UFFDIO_WRITEPROTECT`), and the values are checked.
- This laptop: kernel 7.0.0-38, uid 1000, `vm.unprivileged_userfaultfd` = 0 (so only the
  user-mode-only form is allowed without root, which is the form used).
- Probe results, each built with `-O1 -g` and run once:

  | Build | gcc 13.3.0 | clang 18.1.3 |
  | --- | --- | --- |
  | no sanitizer | exit 0 | exit 0 |
  | `-fsanitize=address` | exit 0 | exit 0 |
  | `-fsanitize=undefined` | exit 0 | exit 0 |
  | `-fsanitize=thread` | exit 139 (crash at start) | exit 20: `mmap at 0x600000000000 gave 0xffffffffffffffff (errno 1: Operation not permitted)` |

- The gcc TSan crash is the address-randomisation problem already seen in M0-1. With
  `setarch x86_64 -R` both compilers give the same result: exit 20, `mmap` refused with errno 1,
  for the full probe and for the mapping alone.
- Why: a TSan build may map memory only inside TSan's own application ranges. A second probe
  under clang TSan tried five addresses for the same 4 GB mapping: `0x600000000000` and
  `0x100000000000` refused; `0x7e0000000000`, `0x550000000000` and `0x10000000000` mapped. So
  it is the address, not the size, userfaultfd or this machine.
- Network namespaces: `ip`, `tc`, `unshare` present; `sch_netem` module on disk, not loaded.
  `unshare --user --map-root-user --net sh -c 'ip link set lo up && tc qdisc add dev lo root
  netem delay 5ms loss 1% && tc qdisc show dev lo'` → `qdisc netem 8001: root refcnt 2 limit
  1000 delay 5ms loss 1%`, exit 0, with no root. `ip netns add` as this user fails
  ("mount --make-shared /run/netns failed: Operation not permitted"), and `sudo -n true` needs
  a password, so the unprivileged user-namespace route is the one that works here.
- Asked the person how to treat TSan; answered (see Questions).
- Next: write `tools/check_env.sh` around the probe, run it here, and force each kind of
  failure to see the non-zero exit.
