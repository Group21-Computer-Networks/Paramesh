### 2026-10-07 — session 2: every item tried by hand; Still open #17 answered

- Wrote a probe in C (scratchpad): `mmap` 4 GB at `0x600000000000` with
  `MAP_FIXED_NOREPLACE`, open userfaultfd with `UFFD_USER_MODE_ONLY`, `UFFDIO_API` asking for
  the write-protect feature, register the whole region for missing and write-protect faults,
  then on the first and the last page: a thread reads (missing fault, answered with
  `UFFDIO_COPY` in write-protect mode) and writes (write-protect fault, answered with
  `UFFDIO_WRITEPROTECT`), and the values are checked.
- This laptop: kernel 7.0.0-38, uid 1000, `vm.unprivileged_userfaultfd` = 0 (so only the
  user-mode-only form is allowed without root, which is the form used).
- Probe results, each built with `-O1 -g` and run once:

  | Build | gcc 13.3.0 | clang 18.1.3 |
  | --- | --- | --- |
  | no sanitizer | exit 0 | exit 0 |
  | `-fsanitize=address` | exit 0 | exit 0 |
  | `-fsanitize=undefined` | exit 0 | exit 0 |
  | `-fsanitize=thread` | exit 139 (crash at start) | exit 20: `mmap at 0x600000000000 gave 0xffffffffffffffff (errno 1: Operation not permitted)` |

- The gcc TSan crash is the address-randomisation problem already seen in M0-1. With
  `setarch x86_64 -R` both compilers give the same result: exit 20, `mmap` refused with errno 1,
  for the full probe and for the mapping alone.
- Why: a TSan build may map memory only inside TSan's own application ranges. A second probe
  under clang TSan tried five addresses for the same 4 GB mapping: `0x600000000000` and
  `0x100000000000` refused; `0x7e0000000000`, `0x550000000000` and `0x10000000000` mapped. So
  it is the address, not the size, userfaultfd or this machine.
- Network namespaces: `ip`, `tc`, `unshare` present; `sch_netem` module on disk, not loaded.
  `unshare --user --map-root-user --net sh -c 'ip link set lo up && tc qdisc add dev lo root
  netem delay 5ms loss 1% && tc qdisc show dev lo'` → `qdisc netem 8001: root refcnt 2 limit
  1000 delay 5ms loss 1%`, exit 0, with no root. `ip netns add` as this user fails
  ("mount --make-shared /run/netns failed: Operation not permitted"), and `sudo -n true` needs
  a password, so the unprivileged user-namespace route is the one that works here.
- Asked the person how to treat TSan; answered (see Questions).
- Next: write `tools/check_env.sh` around the probe, run it here, and force each kind of
  failure to see the non-zero exit.

### 2026-10-07 — session 3: script written and exercised

- Wrote `tools/check_env.sh` (405 lines, bash). It carries the C probe inside itself, builds
  it in a temporary directory with each of gcc and clang that is installed (or `$CC`), and
  prints one line per item: `pass`, `FAIL` with a reason and a hint, or `n/a`. Exit 0 if
  nothing failed, 1 otherwise, 2 for a wrong option. `-v` shows what each probe printed, `-k`
  keeps the temporary directory, `-h` prints the usage.
- The probe has three modes: `map` (the 4 GB mapping alone, run 20 times because the address
  layout changes per run), `uffd` (userfaultfd and both fault kinds on a small mapping the
  kernel places, so the answer does not depend on the region), `full` (both on the region's
  first and last page; also what the sanitizer builds run).
- Run on this laptop: 13 pass, 0 FAIL, 1 n/a, exit 0, in about 1.2 s. Full output under
  Verification.
- Forced each kind of failure without changing the script; every one printed `FAIL` and
  exited 1 (details under Verification). Two fixes came out of that: a stray "Aborted" line
  from bash when a sanitizer build of the probe died (the probe now runs in a subshell whose
  stderr is dropped), and a misleading message when `CC` names a compiler that is not
  installed.
- `shellcheck` is not installed here, so the script was checked with `bash -n` only.
- For M0-8: ASan and UBSan work with the region; TSan does not, on any machine. The tests
  that map the real region must not be registered for the TSan build.
- For the M0 gate: the person runs `tools/check_env.sh` on each of the six laptops; the header
  it prints (host, kernel, system, user) identifies the run.
- State: Done-when met. Not pushed.

## Decisions

<!--
Choices you made inside the card's scope, each with the reason. Not for points listed under
"Still open" in the plan: those are asked, never decided here. Write "None" if there were none.
-->
- **The kernel checks are a C program inside the script.** A shell cannot call userfaultfd, and
  the card allows one file, so the probe is a here-document compiled when the script runs. A
  machine that builds ParaMesh has a C compiler; if none is found the item fails with the
  package to install.
- **Four items beyond the card's six,** each because a later failure would otherwise be
  confusing: 4 KB pages (the design fixes the page size); run as an ordinary user (the
  card's "without root" cannot be shown as root); a C compiler; and faults served on the first
  and last page of the real region, which ties the mapping and userfaultfd items together.
- **Every installed compiler is checked for the sanitizer item,** because Actions builds with
  both gcc and clang and the sanitizer runtimes are separate packages.
- **The address check runs 20 times.** With address-space randomisation one clean run does not
  show the address is reliably free.
- **Network namespaces are tried without root first** (`unshare --user --map-root-user --net`),
  then through passwordless `sudo`. NFR-3 asks for no root, and that route works on this
  laptop.
- **`n/a` is a third outcome,** used once, for ThreadSanitizer, as the person decided.
- **No test in `ctest` runs the script.** It depends on kernel features the hosted runners may
  not give, so a test would fail in Actions for reasons that have nothing to do with the code.
