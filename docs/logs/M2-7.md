### 2026-10-09 — session 2: the program, the script, and runs

- `apps/counter/main.c` (C11) and its build file. Every node adds 1 to one shared number,
  `adds` times (default 1,000): first with `pm_lock` around each read-add-write, then with
  `pm_atomic_add`. The launcher adds on a thread of its own while the workers do, so all
  nodes add at once. The program counts the nodes that took part (each adds 1 to a third
  number) and prints both totals; exit 0 only if both are nodes x adds.
- `tests/multi/counter.sh [build directory]`: three nodes on localhost with 1,000 adds, then
  three in network namespaces with 2 ms on every link and 100 adds. It only calls the two
  scripts of M1-9 and reports PASS if both did.

## Decisions

<!--
Choices you made inside the card's scope, each with the reason. Not for points listed under
"Still open" in the plan: those are asked, never decided here. Write "None" if there were none.
-->
- **The launcher adds too, on a thread of its own.** `pm_test_run_on_workers` blocks `main()`
  until the workers finish, and "three nodes each add" would otherwise be two at a time.
- **The program counts its nodes itself** with `pm_atomic_add`; the API has no call for the
  size of a job, and the scripts choose it.
- **Fewer adds under delay** (100, not 1,000): an add under the lock crosses the delayed links
  about eight times, and the lock makes all of them take turns.
- **The script is a wrapper, not a third runner:** starting, waiting and reporting stay in
  `run_local.sh`.
- **Not a ctest entry,** like the other multi-node tests: the plan keeps them to local scripts.
  The program is built in Actions with everything else.
